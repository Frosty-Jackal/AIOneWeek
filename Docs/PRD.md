# AIOneWeek 产品需求文档（PRD）

版本 v1.0 · MVP · 2026-09-28 · 责任人 frostyj@qq.com

---

## 1. 背景与目标

**背景**

AI 产品经理需持续跟踪前沿技术，但信息分散在 arXiv / HuggingFace / 各厂博客，人工筛选一周要花数小时，且存在时间差失位：RAG（2024）从论文到工业普及约两年，若早期掌握即可抢先落地；26 年 9 月上旬的 Jev 这类大幅降低成本的技术同理。当前痛点三个：**不知道、看漏了、忘光了**。

**目标（业务结果，非功能输出）**

| 指标 | 目标值 |
| --- | --- |
| 普通用户查看当周技术的操作耗时 | ≤ 3 秒看到全部条目，无需自行检索 |
| 周活 AIPM 中至少查看过 1 次当周列表的比例 | ≥ 50% |
| 平均打分 > 3 分的用户占比（见第 5 节） | ≥ 50% |

**反指标（不许恶化）**

- **无用技术率** = 打 2 分及以下的评价数 ÷ 当日已评价数。要求 < 20%（20% 同时是第 8 节评测集回填的触发线）
- **重复率** = 与近 30 天已展示条目重复的技术数 ÷ 当日展示条目数。要求 < 10%

**停止条件**

连续 2 周无用技术率 > 30%，或日均成本连续 2 周超预算 1.5 倍（> ¥0.03/天），则暂停迭代并复盘是否关停。

## 2. 用户与场景

| 角色 | 场景 | 频率 | 现在怎么解决 | 容忍度 |
| --- | --- | --- | --- | --- |
| **AI 产品经理**（核心） | 每天任意时间的电脑屏幕，需把技术映射到工业场景 | 每天 1–2 次 | 刷公众号 / X / arXiv 人工筛 | 3 秒不出结果即放弃；看到 1 条无用技术即降低信任 |
| **AI 开发者** | 工作时间，评估是否引入新模型/技术 | 每周数次 | HuggingFace Trending | 同上 |
| **AI 算法岗**（工业界 + 高校） | 工作时间，跟进 SOTA | 每周数次 | arXiv + 推特 | 对参考链接可达性要求高 |
| **AI/CS/电子信息/SE 学生** | 课后学习入门 | 每周数次 | 视频 / 博客 | 对"这技术能干嘛"要求最高 |

**角色链路**：管理员（种子账号）每天 8:50 定时采集 → 写入日表 → 用户点「查看当周内 AI 前沿技术」→ 补齐缺口 → 展示 → 底部打分 → 回流到管理员数据管理界面。

## 3. 能力边界

**能做**

- 按网站列表采集指定日期的 AI 前沿模型/技术，筛选后结构化输出**最多 5 条**
- 展示六要素：技术名 / 技术内容（应用视角）/ 技术创新 / 应用场景（固定 3 个）/ 发布时间 / 参考链接
- 查看当周（滚动 7 天：当天 + 前 6 天）全部条目
- 邮箱验证码注册、邮箱+密码登录、验证码登录
- 管理员端：网站列表增删改查、手动触发采集、查看用户数据与评分

**不能做（v1 明确不做）**

- 不做全文搜索、分类/标签筛选、订阅推送、收藏
- 不做移动端适配（仅桌面端）
- 不做用户端条目的人工编辑与审核
- 不承诺技术的生产可用性，不提供代码实现

**拒绝输出 / 不硬凑**

- 当天无创新或性能提升不足的技术时，返回「无」，不用旧技术填充
- 采集结果不足 5 条时如实展示

**模型做不到时（降级）**

- 返回「无」或解析失败 → 日表写 `status=empty` / `parse_failed` 的**记录**（不是空值），前端展示「这日无前沿 AI 技术」
- 单次采集失败重试 1 次；仍失败标记 `failed`，不阻塞当周展示

**约束性说明**

| 项 | 约束 |
| --- | --- |
| 输入 | `<今天日期>` 必填；网站列表每行一个 URL |
| 输出 | 单日条目上限 5 条；应用场景固定 3 个 |
| 密码 | 2–8 位，仅数字 + 英文 |
| 验证码 | 4 位数字，有效期 10 分钟，同邮箱发送间隔 ≥ 2 分钟 |

## 4. 功能需求

### P0-1 采集（管理员端）

- **入口 A**：每天 8:50 定时任务（cron）
- **入口 B**：管理员点「获取 &lt;日期&gt; 的 AI 前沿技术」按钮
- **实现**：调用 **DeepSeek Anthropic 兼容端点**（`https://api.deepseek.com/anthropic/v1/messages`，认证头 `x-api-key`），`tools=[{"type": "web_search_20250305", "name": "web_search"}]`，模型 `deepseek-flash`
  - ✅ 2026-09-28 实网探测：`/responses` 的内置工具被官方文档标注为「忽略」，`web_search` 在该端点**静默失效**（返回 200 但 `output` 无任何搜索项，`input_tokens` 仅 56）；Anthropic 兼容端点返回真实的 `server_tool_use` + `web_search_tool_result`。详见 Spec1 §5.2
  - prompt 见附录 A；`<爬的网站列表>` 从 `source_sites` 表读取
- **幂等性**：同一日期重复触发时，若 `daily_tech` 已有 `success` 记录，直接返回缓存**不重复调 API**（除非管理员勾选「强制刷新」）
- **返回后**：用 Python 做结构化提取（按 `【】` 分隔符解析）→ 落库 `daily_tech`

### P0-2 网站列表管理（管理员端）

- `source_sites` 表 CRUD，支持启用/停用
- 初始一行：`https://huggingface.co/papers/trending`

### P0-3 用户端主界面

- 按钮「查看当周内 AI 前沿技术」
- **逻辑**：查 `daily_tech`，检查滚动 7 天（当天 + 前 6 天）是否每天都有记录
  - **有缺口** → 对每个缺失日期走 P0-1 采集 → 补齐后展示
  - **无缺口** → 直接查库展示，**不调 API**
  - **判定规则**：`status=success` 且有条目 = 有数据；`status=empty`（返回「无」）= **也算有数据**，不是空
- **展示**：按日期倒序分组的条目卡片

### P0-4 鉴权

- 用户点主界面时才鉴权，未登录弹登录弹窗（不跳页）
- **邮箱 + 密码**为主方式；弹窗下方附「验证码登录」和「注册账号」
- **注册流程**：填邮箱 → 后端生成 4 位验证码 → 用 `frostyj@qq.com` 发送（主题「AIOneWeek验证码」，正文「您的验证码为：xxxx」）→ 表单提交时校验验证码 → 设 2–8 位数字+英文密码 → 落库
- 同一邮箱只能注册一次；验证码发送间隔 ≥ 2 分钟
- **管理员账号**：种子脚本预置，不开放注册，`role=admin`

### P1-1 评分（用户端）

- 展示区底部「您对本次获取满意吗？」，1–5 分共 5 个按钮
- 选择后 5 秒内可更改；5 秒无新操作则上传

### P1-2 数据管理界面（管理员端）

- 管理员有两个界面：「主界面」+「数据管理界面」；用户只有「主界面」
- 用户列表（可下滑）：邮箱 / 密码（解密后显示）/ 调用次数 / 平均打分
- 平均打分 = Σ(分数 × 该分数出现次数) ÷ 总评价次数

**接口语义**

| 接口 | 幂等 | 超时 |
| --- | --- | --- |
| `POST /api/collect?date=YYYY-MM-DD` | 是，重复调用返回已有结果 | 单次 30s，重试 1 次 |
| `GET /api/weekly` | 是，只读 | 无缺口 3s；含补采 120s（前端需 loading） |

补采串行执行，最多 7 次调用。

**埋点**：不设（理由见第 8 节）。

## 5. 评测标准

- **评测集**：`eval_set` 表，初始 0 条，由反指标触发自动回填（见第 8 节）
- **通过线**：管理员人工抽检准确率 ≥ 80%（条目真实存在、创新点描述属实），方允许灰度
- **线上指标**：平均打分 > 3 分的用户占比 ≥ 50%
- **指标公式**：`平均打分 = Σ(score_i × count_i) ÷ Σ(count_i)`；观测周期 = 自然周；分子分母均为「当周已评价用户」
- **人工抽检**：每周抽 10 条当周条目，核对参考链接是否可达、创新点是否成立，错误回填评测集
- **红队**：v1 不做（无用户自由输入，prompt 由管理员控制，提示注入面小）

## 6. 失败路径与兜底

| 失败 | 表现 | 兜底 |
| --- | --- | --- |
| **无技术**（最高频） | 模型返回「无」 | 日表写 `status=empty`，前端展示「这日无前沿 AI 技术」；当周展示继续，不报错 |
| 模型幻觉 | 编造技术名或不可达链接 | 输出固定六字段，前端统一标注「AI 生成，请核验参考链接」；人工抽检回填评测集 |
| 采集超时 | 单次 API > 30s | 重试 1 次；仍失败写 `status=failed`，前端展示「该日采集失败，管理员可在管理端重试」 |
| 解析失败 | 返回不符模板格式 | 原始返回存入 `raw_response` 字段，标记 `status=parse_failed`，管理员可手动修正 |
| 工具调用未执行 | thinking 模式下模型只"描述"调用 | 检测 `content` 中无 `server_tool_use` + `web_search_tool_result` 即判定失败，走重试（Spec1 §5.2） |
| 上游限流 / 额度不足 | 429 / 余额不足 | 停止本轮补采，展示已成功日期，缺口提示「XX 日数据待补」 |
| 成本超限 | 日成本 > ¥0.03（预算 1.5 倍） | 降级：关闭 `web_search`，仅用模型已有知识输出，条目标注「未经联网核验」；连续 2 周超限触发第 1 节停止条件 |
| 邮件发送失败 | SMTP 报错 | 前端提示「验证码发送失败，请稍后重试」；同码不重发 |
| 鉴权失败 | 密码错误 / 未登录 | 弹窗内提示错误，不跳转页面 |

**关于人工兜底**：本产品不提供在线人工客服，也不设「转人工」入口。所有需人工介入的场景收敛到管理员端 —— 管理员可在数据管理界面重试采集、修正解析失败条目。用户可在登录界面看到客服邮箱 `frostyj@qq.com`（用户端登录 / 验证码登录 / 注册三个视图下均常驻，管理端登录框同样显示），但 **v1 不承诺响应时限**。

## 7. 成本预算

| 项 | 估算（2026-09-28 实测口径） |
| --- | --- |
| 单次采集 | 实测 17,521 input + 1,235 output tokens；`deepseek-flash` 闲时 $0.15 / $0.6 每 1M ≈ **¥0.024**；峰时翻倍 ≈ **¥0.048** |
| **单日** | 默认 1 次定时采集 ≈ **¥0.024–0.048** |
| 单月 | ≈ **¥0.7–1.4/月** |
| 峰值假设 | 冷启动一次补满 7 天且全落峰时 ≈ **¥0.34/天** |

> 计费按 **token**，无「按次搜索费」；原「$0.0005/次」的估算口径不适用于本端点。

**缓存策略**

- `daily_tech.date` 建唯一索引，同日不重复调 API（结果缓存）
- prompt 前缀固定，提高模型侧 prompt 缓存命中

**成本护栏**：日成本 > **¥2.0** 触发降级（见第 6 节）。依据：最坏 7 天补采 ≈ ¥0.34，¥2.0 使护栏回到「异常兜底」语义而非每日必然触发的限流。原 ¥0.03 会被单次调用（¥0.024–0.048）直接击穿。详见 Spec1 §9。

## 8. 数据与反馈

**埋点**：不设。理由：核心行为（查看、评分）已由业务接口天然记录，MVP 阶段不引入额外埋点成本。

**用户反馈回流**：评分（1–5）选择后 5 秒上传，写入 `rating` 表，汇总展示在管理员数据管理界面。

**评测集回填**：若当天「已点获取当周**且已评价**」的用户中，打 2 分及以下的比例 > 20%

> `低分人数 ÷ 已评价人数 > 0.2`（已评价人数 = 0 时不触发）

则把**当次采集的 prompt** 连同**日期**写入 `eval_set` 表。存住即可，暂不做前端展示。

**数据表**

| 表 | 字段 |
| --- | --- |
| `users` | id, email, password_enc, role, call_count, created_at |
| `source_sites` | id, url, enabled, created_at |
| `daily_tech` | id, date(唯一), tech_name, tech_content, innovation, scenarios, publish_date, ref_link, status, raw_response, created_at |
| `rating` | id, user_id, date, score, created_at |
| `eval_set` | id, date, prompt, created_at |
| `verify_code` | id, email, code, expire_at, created_at |
| `admin_audit` | id, admin_id, action, target, created_at |

`status` 取值：`success` / `empty` / `failed` / `parse_failed`

- **责任人**：frostyj@qq.com，有权一键回滚至「仅管理员可用」

## 10. 合规与风控

- **邮箱、密码**：AES 对称加密存储于本地数据库。管理员在数据管理界面需点击「查看」方可解密，**每次解密操作写入 `admin_audit` 日志**（谁、何时、看了哪条）
  - 已知残余风险：可逆加密意味着密钥泄露即全量明文泄露。缓解措施为密钥与数据库分离存储、解密操作全程留痕
- **模型与 prompt 版本**：纳入 GitHub 版本管理，prompt 变更留痕，回答「谁在何时改了什么」
- **数据用途**：邮箱/密码仅用于登录鉴权；评分数据用于评测；采集结果用于展示
- **保留期**：10 年；到期删除机制留待后续迭代
- **内容安全**：所有展示条目统一标注「AI 生成，请核验参考链接」；参考链接指向原始来源，不转载全文
- **地区差异**：v1 仅面向中国大陆用户，数据存储于本地；出海合规检查项留待 v2
- **审计**：`admin_audit` 表记录管理员全部写操作（触发采集、改网站列表、解密密码）

| 决策 | 结论 | 理由 |
| --- | --- | --- |
| 当周范围 | 滚动 7 天（当天 + 前 6 天） | 语义上正好是「一周」，跨天体验连续 |
| 密码存储 | AES 可逆加密，管理员可查 | 保留管理员查看能力，风险由审计日志缓解 |
